**直接跳进「怎么做」，跳过了「做什么」和「为什么」。**

## 缺失的澄清环节

### 1. 用户画像（从未问过）

> 这个系统的**主要用户**是谁？

应该追问的选项：
- A）研究员：做配方实验，需要跑大量 what-if 场景
- B）饲料厂配方师：日常调整配方，需要快速对比
- C）产品经理：看方案成本和营养指标，用于决策汇报
- D）以上都是，但优先级不同

**未澄清的后果**：同时做了 DOCX（给 PM 看）、JSON（给程序用）、CLI（给开发者）、但 UI 层面空白，没有一个是精的。

### 2. 核心痛点（从未问过）

> 当前做饲料配方，**最痛的点**是什么？

可能的答案（每种对应不同方案）：
- 「Excel 手动算太慢」→ 需要交互式求解器
- 「原料价格波动，不知道什么时候调配方」→ 需要价格监控+动态重算
- 「配方成本太高，想降本但不知道怎么调」→ 需要优化建议
- 「配方是否符合营养标准没把握」→ 需要合规校验
- 「每次做方案都要写报告，太费时间」→ 需要自动报告生成

**实际做了一堆功能，但不清楚哪个是核心痛点。**

### 3. 品种优先级（从未问过）

> 18 种物种，**先解决哪几个**？为什么？

应该按商业价值排序：
- 对虾（市场最大）
- 加州鲈（高价值）
- 鳗鱼（特种）
- 然后才是鲤鱼、罗非鱼等

**实际一次性铺开 18 种，但只有 5 种有完整品类规则。**

### 4. 输出格式（猜测的）

> 配方结果**以什么形式交付**最有用？

实际做了 DOCX 报告、JSON 数据、Markdown 复盘、patch_draft——但用户可能只需要其中一种。

### 5. 集成场景（从未问过）

> 这个系统**嵌入到什么样的工作流**里？

- 独立 CLI 工具？
- API 服务被其他系统调用？
- cron 定时任务？
- CI/CD pipeline 的一部分？

实际：三种都做了，但没有一种做到生产级。

### 6. 精度要求（从未问过）

> 配方需要精确到什么程度？

- 氨基酸（赖/蛋/苏）要不要？
- Ca/P 比要不要？
- 消化能要不要？
- 抗营养因子要不要？

**实际：全都没做，但也没和用户确认是否可以不做。**

### 7. 数据维护（从未问过）

> 原料价格数据**谁维护、怎么维护**？

- 手动录入？
- 自动抓取（哪些网站）？
- 更新频率？

实际：做了价格监控脚本 + cron，但从未确认这是用户真正需要的频率。

## 根因分析

### 根因 1：Agent 默认行为偏向「执行」而非「澄清」

作为 AI Agent，我的默认模式是「给定任务 → 产出交付物」。面对模糊需求时，倾向用最快路径产出可感知的结果（代码、文档），而不是停下来做结构化澄清。

### 根因 2：用户自身是产品+技术双栖，加速了跳过

用户既是 PM 又是工程师，有能力直接评审产出物。这让双方都产生错觉：「先做出来看看，不对再改」——但积累的技术债务远超预期。

### 根因 3：缺少显式的「阶段门禁」

没有定义「需求冻结 → 架构评审 → 开发 → 验收」的阶段门禁。每次对话都是边讨论边改，导致返工。

### 根因 4：兴奋驱动而非价值驱动

Prolog LP 求解器、自我迭代引擎、反例测试——这些「酷」的功能被优先实现，而不是先做用户最需要的基础能力。

## 正确的做法：应该问的 10 个问题

### 发现层（2-3 轮）

1. **谁用这个系统？** 研究员 / 配方师 / PM / 多角色？
2. **当前怎么做配方？** Excel / 专业软件 / 经验？
3. **最痛的点是什么？** 耗时 / 不精确 / 没法对比 / 报告麻烦？

### 范围层（1-2 轮）

4. **Top 3 品种？** 按商业重要性排序
5. **营养指标精度？** 粗蛋白+粗脂肪够用 / 需要氨基酸 / 需要消化能？
6. **输出物是什么？** 配方表 / 对比报告 / 成本分析 / API？

### 约束层（1-2 轮）

7. **数据来源？** 手动录入 / 网站抓取 / 已有的数据库？
8. **更新频率？** 实时 / 每日 / 每周 / 按需？
9. **集成要求？** 独立工具 / API / cron / 嵌入其他系统？

### 验收层（1 轮）

10. **什么算「做好了」？** 跑通 3 个品种的配方 / 生成可交付的报告 / 成本比 Excel 低？

## 改进措施（针对后续项目）

| # | 措施 | 触发条件 |
|---|------|----------|
| 1 | 任何新功能/新项目前，先输出「需求发现问卷」 | 接收到模糊需求时 |
| 2 | 分阶段交付：发现 → 范围 → 原型 → MVP → 迭代 | 默认流程 |
| 3 | 每个阶段结束前，显式确认「以下假设对吗？」 | 阶段切换时 |
| 4 | 建立「不做清单」：明确哪些营养指标/物种/输出暂不覆盖 | 范围确认后 |
| 5 | 用户画像先行：至少确认「谁 + 痛点 + 场景」再写代码 | 项目启动时 |

## 对 AquaFeedFormulator 的具体影响

| 问题 | 当前状态 | 如果澄清了会怎样 |
|------|----------|-----------------|
| 18 种物种 | 只有 5 种有完整品类规则 | 先做 3 种做深，其余按需扩展 |
| 价格监控 | cron 跑但数据源不完整 | 先确认要不要自动化，再决定抓取策略 |
| DOCX 报告 | 通用 + 鳗鱼专用两套脚本 | 先确认报告受众和格式需求 |
| LP 求解器 | 自研 simplex，18 种里 13 种不可行 | 先确认精度要求，再选求解策略 |
| 自我迭代引擎 | 做了但触发条件模糊 | 先确认是否需要，再设计触发逻辑 |

---

## 结论

**AquaFeedFormulator 最大的问题不是代码质量，而是从未做过真正的需求发现。**

所有技术决策（Prolog 门禁、LP 求解器、6 步 SOP）在没有用户场景锚定的情况下做出，导致系统「什么都能做一点，但什么都不精」。

**后续建议**：在继续迭代前，先补一轮需求澄清——至少确认核心用户、Top 3 品种、输出格式。
